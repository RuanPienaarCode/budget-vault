Accounts and transaction folders

How a transaction row finds the account it belongs to, how a bank statement finds the folder it should land in, and the two ways those can silently disagree. Both traps below are real: each was found in a live vault, and neither shows an error when it happens.

The three names an account has

An account is a markdown file. Its transactions are somewhere else entirely — a folder of monthly files under Transactions/. Nothing links them but a string, and an account can be known by three:

NameWhere it livesWhat it is
namethe filename, Accounts/Baby Fund.md What the reader calls the account. The default for everything else.
tx_labelfrontmatter An override, for when the transaction folder is named differently from the account. Optional, and most vaults never need it.
account_numberfrontmatter The bank's own number. Used to route a statement file and to recognise transfers — see below.

Reading: folder → account

accountForLabel() in src/period.js takes a folder name and finds the account that claims it. Three tests, first match wins:

a.tx_label === label            // the explicit override
|| a.name === label             // the account's own name
|| safeSeg(a.name) === safeSeg(label)   // the same name, filesystem-cleaned

The third exists because safeSeg() strips characters a folder name cannot carry, so an account named Ruan / Christine lives in a folder that is not spelled that way. A folder no account claims returns null — see trap 2.

Writing: statement → folder

detectAccountLabel() in src/views/import.js goes the other way. It reads the account number out of the filename (DiscoveryBank_12345678901_….csv), finds the account carrying it, and returns one name to import into:

acc.tx_label || acc.name
The asymmetry is the whole problem

Reading accepts three names. Writing produces one. So an account can read its rows perfectly from a folder that imports would never write to — and nothing on any screen says so.

Trap 1 — a tx_label naming a folder that does not exist

Set tx_label to something no folder is called and everything keeps working. The account's existing rows still resolve, by the name match. Totals are right. Reconciliation is right. Nothing is wrong until the next import.

Then the importer writes to tx_label — a folder that does not exist — and creates it. The account now has two folders. Both resolve back to it, so the totals still look sane. But the importer's duplicate key is date|desc|amount|label, and the label is new, so nothing matches: every row in the statement imports again as brand new.

Seen live, 10 Aug 2026

An account named Baby Fund held 271 rows in Transactions/Baby Fund/ and carried tx_label: "Easy Accees Savings" — a folder that had never existed, misspelling and all. Everything read correctly for as long as nobody imported. Correcting the spelling would have made it worse, not better: the import would have created Easy Access Savings/ and duplicated all 271 rows. The fix was to point tx_label at the folder that actually holds the rows.

The rule: tx_label must name a folder that exists, or be absent. It is an override for a real mismatch, not a display name. When the folder matches the account name — the normal case — leave it out or set it to the name.

Trap 2 — a folder no account claims

The mirror failure. A folder under Transactions/ that matches no account by any of the three names is an orphan. accountForLabel() returns null and accountIndex() skips it entirely.

Its rows are not lost — Transactions lists them, and period totals count them like any other row. But they are invisible to everything that reasons about accounts:

  • they contribute nothing to any account balance
  • they never appear in a reconciliation, so the drift they cause is never explained
  • they are absent from the cash figure behind “What’s left”

This is deliberate — the loader will not invent an account for a folder — but it is silent, and a folder created by hand or left behind by a renamed account can sit there for years.

account_number does two jobs

It is optional, and a vault works without it. What it buys:

  1. Routing. A statement named after the account number lands in the right folder with no prompt. Without it the reader picks the account by hand on every import.
  2. Transfer recognition. counterpartyAccount() in src/statement.js reads digit runs out of a transaction description and matches them against every account's number. A hit means the row is money moving between the reader’s own accounts, so it imports pre-excluded rather than counted.
The cost of leaving it out

Without account_number on both sides, a transfer between two of the reader’s own accounts imports as income on the receiving side. The household then appears to have earned its own savings, and the Dashboard reports a month it did not have. Matching is exact on runs of four or more digits, never fuzzy — a wrong match here would silently delete a real income figure.

Checking a vault

Neither trap raises an error, so both have to be looked for. Two questions, and both should return nothing:

There is a script for it, because the shell one-liners this section first carried were wrong in both directions — they reported every account with no folder yet as misrouted, and mis-escaped folder names with brackets in them as orphans. The script uses the same three-name rule accountForLabel() does:

node scripts/check-account-folders.cjs "<vault>/<budget folder>"

It exits non-zero on any finding, so it drops into a pre-commit hook or CI unchanged. Read-only.

An account with no folder at all is not a finding. That is simply an account nothing has been imported into — the normal state of a hand-tracked fund, and the case the first version of this check got wrong.

The one-line rule

An account’s tx_label, if present, must be the name of a folder that exists — because reading forgives a wrong one and writing does not.
