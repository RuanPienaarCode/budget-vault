How a period is decided — shape, phase and income

The two ADRs record what was decided: that periods are derived rather than materialised, and that the pay cycle is a number, not a name. This one draws how it runs, after 1.3.1 and 1.3.2 closed the gap that let the app sit on a date which was no longer the start of anything. Three diagrams: which shape names a period, why phase matters as much as shape, and how a monthly income figure is derived when the period isn't a month.

The gate: which shape names a period

Two settings decide everything. period_anchor is one known payday; period_days is the cycle length. Either one being unusable drops the pair and the vault runs payday months — the behaviour every vault had before pay cycles existed.

Phase, drawn — why a date-shaped name is not enough

This is what 1.3.1 fixed. A period name is a date, but not every date is the start of a period: only those a whole number of cycles from the anchor. Changing the cycle length redraws that set, and the old check — which only asked "is it shaped like a date?" — kept saying yes.

What that cost, before the fix
The dates on screen straddled two periods, so totals matched neither. The arrows walked the off-phase track indefinitely — only jump to current period escaped. A budget saved while off-phase wrote a file no later period could open, and the Budgets page did not list it among the ones waiting, because it passed this very check. Moving the last-payday date by a few days did the same thing by a different route.

The three checks a period name now passes

All three live in one function, periodKeyValid(), which the loader calls on every startup and after every settings change. Failing any of them resets to the current period.

#CheckRejectsWhy it exists
1 Shape matches the active period type 2026-08 on a pay cycle · 2026-08-07 on payday months The two shapes are not interchangeable. A month name on a 14-day cycle yields a 31-day window and navigates to another month name.
2 It is a real calendar date 2026-13-45 · 2026-02-30 · 2026-13 Date rollover turns these into a real window the name never described — 2026-13 rendered as a navigable month titled “undefined 2026”.
3 It is on phase with the anchor new in 1.3.1 2026-08-14 on a 14-day cycle anchored 2026-08-07 The one drawn above. (day − anchor) % cycle === 0, so only genuine period starts survive a length change or an off-cycle anchor move.
The same rule now backs the reassurance
The settings notice — “your existing budget files stay in the vault” — counts the files the incoming length genuinely can’t reach, using this same phase test. It used to say nothing at all when both lengths were cycles, which silently covered the one case that strands half your files: weekly → every two weeks.

Income when the period isn’t a month

The Debt page has to talk in months no matter what the period length is: an instalment is quoted monthly, and the 36% lenders use only means anything against a month. Scaling one period up works when income lands every period — which is the fortnightly case it was written for. On a weekly cycle a monthly salary lands one week in four.

Why the window is 13 weeks and not 12 or 14

The window length is chosen so it lands as close as possible to a whole number of months — not simply “about three months”. A ragged window catches three paydays in some weeks and four in others, which puts a 33% step into a number that should barely move.

A young vault is not divided by silence
Periods with no transactions at all are trimmed off the back of the window before the division, so a vault whose data starts three weeks ago still reports its one week scaled up — exactly as before — rather than averaged into near-nothing. A gap inside the window still counts as zero, because there the silence is real.

What is still not guarded

Written down so each is a decision rather than an oversight, and tracked so neither has to be rediscovered. Every one is open on the issue tracker — follow the number on each row.

knownSettings can show a cycle the app is not running#2

The settings tab reads Settings.md directly, so a file with period_days: 14 and no usable anchor displays “Every 2 weeks” while the vault runs payday months. Deliberate in part — the tab reports a hand-set length truthfully rather than snapping it to a preset — but nothing says so on open. A notice fires only when the dropdown is touched. Pre-dates 1.3.1; fixing it well means a warning line in the tab, not a logic change.

theoreticalYear 0000–0099 in a period name#3

isRealIsoDate() rejects a two-digit year, because Date maps 0–99 onto 1900–1999 and the round-trip catches the relocation. The month-name check does not carry the same guard, so a hand-made Budgets/0000-01.md would resolve to December 1899. Left alone: no such file can arise from the app, and guarding it costs more comment than it saves.

by designOff-phase budget files stay unreachable#4

They are named, counted and offered for structure carry-over — but their amounts cannot be opened until the old length is restored. That is the honest outcome: an amount budgeted for a fortnight is not an amount for a week, and guessing which lines halve cleanly is exactly what the app refuses to do elsewhere.

trade-offA 126-day window lags a real income change#5

On a fortnightly cycle the averaging window is about four months, so a raise or a job change takes that long to show fully in the debt-to-income ratio. Accepted: on that cycle income arrives every period, so the window length barely affects the figure — and the alternative windows are further from a whole number of months, which is the error that actually moves the number.
